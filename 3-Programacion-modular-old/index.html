    Programación Modular

    3. Programación Estructurada

    A finales de los 60, el software era un caos. Los programadores usaban una instrucción llamada GOTO que permitía saltar de cualquier punto del programa a cualquier otro. El resultado era el famoso "código espagueti": un lío de saltos imposible de seguir, depurar o mantener.

    El GOTO es el Lado Oscuro

    Edsger Dijkstra, uno de los padres de la informática, escribió en 1968 un famoso artículo llamado "Go To Statement Considered Harmful" (La sentencia GOTO considerada dañina). Demostró que su uso indiscriminado era una de las principales fuentes de errores en programación.

    La programación estructurada nació como la solución a este caos. El Teorema del Programa Estructurado (de Böhm y Jacopini) demostró matemáticamente que cualquier algoritmo, por complejo que sea, puede construirse usando únicamente tres estructuras de control básicas:

    1. Secuencia: Ejecutar instrucciones una detrás de otra.
    2. Selección (o Condicional): Elegir entre dos o más caminos de ejecución (if, switch).
    3. Iteración (o Bucle): Repetir un bloque de código (while, for).

    Estos tres pilares son la base de casi todos los lenguajes de programación modernos, incluido JAVA. Dominarlos es dominar la lógica fundamental de la programación.

    7. Programación Modular

    A medida que los programas crecen, meter todo el código dentro del método main se vuelve una pesadilla. La programación modular es la solución: consiste en descomponer un problema grande en subproblemas más pequeños y manejables, y crear "módulos" de código para resolver cada uno. En JAVA, estos módulos son los métodos (que engloban tanto funciones como procedimientos).

    La Filosofía del "Divide y Vencerás"

    Es mucho más fácil resolver 10 problemas pequeños que un problema gigante. La programación modular aplica este principio para crear software que es: * Más legible: Cada método tiene una única responsabilidad. * Más reutilizable: Un método bien hecho se puede llamar desde distintas partes del programa, o incluso desde otros programas. * Más fácil de depurar: Si algo falla, puedes aislar el problema en un método específico en lugar de buscarlo en miles de líneas de código.

    7.1. Funciones (Métodos que devuelven un valor)

    Una función es un bloque de código que realiza una tarea y, al finalizar, devuelve un resultado. Es como una máquina expendedora: le metes "dinero" (parámetros) y te devuelve un "producto" (el valor de retorno).

    Anatomía de una función en JAVA:

    // <modificadores> <tipo_de_retorno> <nombreDelMetodo>(<lista_de_parámetros>) {
//     // Cuerpo del método
//     return valor; // El tipo de 'valor' debe coincidir con <tipo_de_retorno>
// }

    Ejemplo: Una función que calcula el daño de un ataque en un RPG

    public class CombateRPG {

    /**
     * Calcula el daño final de un ataque.
     * @param fuerzaAtacante La fuerza del personaje que ataca.
     * @param defensaObjetivo La defensa del personaje que recibe el golpe.
     * @return El daño total infligido (un número entero).
     */
    public static int calcularDaño(int fuerzaAtacante, int defensaObjetivo) {
        int dañoBase = fuerzaAtacante * 2;
        int dañoReducido = dañoBase - defensaObjetivo;

        // Nos aseguramos de que el daño no sea negativo
        if (dañoReducido < 0) {
            dañoReducido = 0;
        }

        return dañoReducido; // Devuelve el resultado del cálculo
    }

    public static void main(String[] args) {
        int fuerzaHeroe = 50;
        int defensaOrco = 30;

        // Llamamos a la función y guardamos el resultado en una variable
        int dañoInfligido = calcularDaño(fuerzaHeroe, defensaOrco);

        System.out.println("El héroe ataca al orco e inflige " + dañoInfligido + " puntos de daño."); // Imprime 70
    }
}

    7.2. Procedimientos (Métodos que no devuelven valor)

    Un procedimiento es un bloque de código que realiza una acción, pero no devuelve ningún resultado. Su tipo de retorno se especifica con la palabra clave void. Piensa en él como un botón que, al pulsarlo, hace algo (como encender una luz), pero no te da nada a cambio.

    Ejemplo: Un procedimiento que muestra la barra de vida de un personaje

    public class InterfazUsuario {

    /**
     * Dibuja una barra de vida en la consola.
     * Es un procedimiento porque solo realiza una acción (imprimir), no calcula ni devuelve nada.
     * @param nombrePersonaje El nombre del personaje.
     * @param vidaActual La vida actual.
     * @param vidaMaxima La vida máxima.
     */
    public static void mostrarBarraDeVida(String nombrePersonaje, int vidaActual, int vidaMaxima) {
        System.out.print(nombrePersonaje + " HP: [" + vidaActual + "/" + vidaMaxima + "] ");
        // Dibujamos la barra
        String barra = "";
        for (int i = 0; i < vidaMaxima; i++) {
            if (i < vidaActual) {
                barra += "=";
            } else {
                barra += "-";
            }
        }
        System.out.println("[" + barra + "]");
    }

    public static void main(String[] args) {
        // Llamamos al procedimiento para que realice su acción
        mostrarBarraDeVida("Héroe", 7, 10);
        mostrarBarraDeVida("Orco", 3, 10);
    }
}

// Salida esperada:
// Héroe HP: [7/10] [=======---]
// Orco HP: [3/10] [===-------]

    8. Parámetros

    Los parámetros son la forma que tenemos de pasar información a nuestros métodos. Son las "materias primas" que necesita un método para poder trabajar.

    8.1. Paso por Valor vs. Paso por Referencia

    Este es uno de los conceptos más importantes y que más confusiones genera. Es crucial entender cómo JAVA maneja los parámetros.

    Definición: Paso por Valor

    Cuando se pasa un parámetro por valor, el método recibe una copia del dato original. Cualquier modificación que se haga a esa copia dentro del método no afecta a la variable original fuera del método.

    Definición: Paso por Referencia

    Cuando se pasa un parámetro por referencia, el método recibe la dirección de memoria del dato original. Cualquier modificación que se haga dentro del método sí afecta a la variable original.

    graph TD
    A[Paso por Valor] --> B[Copia del valor]
    A --> C[Modificaciones no se reflejan]
    D[Paso por Referencia] --> E[Dirección de memoria]
    D --> F[Modificaciones afectan original]

    La Regla de Oro en JAVA:

    ¡En JAVA, todo se pasa SIEMPRE por valor!

    Sí, has leído bien. Pero hay un matiz muy importante: * Para los tipos primitivos (int, double, boolean, etc.), se pasa una copia del valor literal. * Para los objetos (incluidos los arrays y Strings), lo que se pasa por valor es una copia de la referencia (la dirección de memoria).

    ¿Qué significa esto en la práctica?

    sequenceDiagram
    participant CodigoPrincipal as "main()"
    participant Metodo as "miMetodo()"

    CodigoPrincipal->>CodigoPrincipal: int vida = 100;
    Note right of CodigoPrincipal: 'vida' contiene el valor 100

    CodigoPrincipal->>Metodo: recibirDaño(vida);
    Note right of CodigoPrincipal: Se crea una COPIA de 'vida'<br>llamada 'daño' con valor 100
    Metodo->>Metodo: daño = 90;
    Note left of Metodo: La copia 'daño' ahora vale 90.<br>La 'vida' original sigue valiendo 100.
    Metodo-->>CodigoPrincipal: finaliza

    CodigoPrincipal->>CodigoPrincipal: System.out.println(vida);
    public class PasoDeParametros {

    // Este método recibe un tipo primitivo (int).
    public static void atacar(int vidaEnemigo) {
        System.out.println("  -> Dentro de atacar, la vida del enemigo es: " + vidaEnemigo);
        vidaEnemigo -= 20; // Modificamos la COPIA
        System.out.println("  -> Después del golpe, la vida es: " + vidaEnemigo);
    }

    // Este método recibe un tipo de objeto (array).
    public static void envenenar(int[] statsEnemigo) {
        System.out.println("  -> Dentro de envenenar, la fuerza del enemigo es: " + statsEnemigo[0]);
        // Modificamos el contenido del objeto al que apunta la referencia
        statsEnemigo[0] -= 5;
        System.out.println("  -> Después del veneno, la fuerza es: " + statsEnemigo[0]);
    }

    public static void main(String[] args) {
        // --- Paso por valor con PRIMITIVOS ---
        int vidaOrco = 100;
        System.out.println("Vida del Orco antes de llamar a atacar: " + vidaOrco);
        atacar(vidaOrco);
        System.out.println("Vida del Orco después de llamar a atacar: " + vidaOrco); // ¡Sigue siendo 100!

        System.out.println("\n-----------------\n");

        // --- Paso por "valor de referencia" con OBJETOS ---
        int[] statsOrco = {50, 20}; // [fuerza, defensa]
        System.out.println("Fuerza del Orco antes de llamar a envenenar: " + statsOrco[0]);
        envenenar(statsOrco);
        System.out.println("Fuerza del Orco después de llamar a envenenar: " + statsOrco[0]); // ¡Ha cambiado a 45!
    }
}

    La analogía: * Paso de primitivos: Te doy una fotocopia de mi número de teléfono. Si tú tachas la fotocopia, mi número original en mi agenda sigue intacto. * Paso de objetos: Te doy una fotocopia de la dirección de mi casa. No puedes cambiar la dirección para que apunte a otra casa (no puedes reasignar la referencia), pero sí puedes ir a esa dirección y pintar la puerta de verde (modificar el estado del objeto). Mi casa (el objeto original) ahora tendrá la puerta verde.


    9. Ámbito de las Variables (Scope)

    El ámbito o scope de una variable define en qué partes del programa esa variable es visible y se puede utilizar. Es como el rango de acción de un personaje en un juego de estrategia: solo puede atacar a enemigos que estén dentro de su alcance.

    graph TD
    A[Ámbito] --> B[Global]
    A --> C[Local]
    C --> D[Función]
    C --> E[Bloque]

    En JAVA, el ámbito está definido principalmente por las llaves {}.

    • Variable de Clase (o Miembro/Atributo): Se declara dentro de una clase, pero fuera de cualquier método. Si lleva la palabra static, pertenece a la clase en sí. Si no, pertenece a cada objeto (instancia) de la clase. Es accesible desde cualquier método de esa clase.
    • Variable Local: Se declara dentro de un método o de un bloque de código (como un if o un for). Solo existe y es accesible desde el punto en que se declara hasta que se cierra la llave } que delimita su bloque.
    public class AmbitoDeVariables {

    // 1. Variable de clase (static). Es "global" para esta clase.
    // Accesible desde cualquier método de esta clase.
    static String nombreDelJuego = "La Leyenda de DAW";

    public static void metodoA() {
        // 2. Variable local al método A.
        int variableA = 100;
        System.out.println("Desde A, puedo ver la variable de clase: " + nombreDelJuego);
        System.out.println("Desde A, puedo ver mi variable local: " + variableA);
        // System.out.println(variableB); // ¡ERROR DE COMPILACIÓN! variableB no existe en este ámbito.
    }

    public static void main(String[] args) {
        metodoA();

        // 3. Variable local al método main.
        int variableMain = 50;

        if (variableMain > 10) {
            // 4. Variable local al bloque if.
            String variableBloqueIf = "Solo existo aquí dentro.";
            System.out.println(variableBloqueIf);
        }

        // System.out.println(variableBloqueIf); // ¡ERROR DE COMPILACIÓN! Ya no existe fuera del if.
        // System.out.println(variableA); // ¡ERROR DE COMPILACIÓN! variableA solo existe dentro de metodoA.
    }
}

    La regla del mínimo ámbito posible

    Una de las mejores prácticas en programación es declarar las variables en el ámbito más reducido posible. Si solo necesitas una variable dentro de un bucle for, declárala dentro del for. Esto evita efectos secundarios no deseados y hace que el código sea mucho más fácil de entender y mantener.

    Reflexión

    1. ¿Por qué crees que es una mala idea usar muchas variables de clase (globales)? ¿Qué problemas podrían causar en un proyecto grande con muchos programadores?
    2. En un bucle for (int i = 0; i < 10; i++), ¿cuál es el ámbito de la variable i?
    3. Si declaras dos variables locales con el mismo nombre en dos métodos diferentes, ¿habría algún problema? ¿Y si una es local y la otra es de clase? (Esto último se llama "shadowing" o sombreado).
