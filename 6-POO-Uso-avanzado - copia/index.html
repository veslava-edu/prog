    POO Avanzada en Java

    ¡Hola, futuros cracks del desarrollo! En el tema anterior, pusimos los cimientos de la Programación Orientada a Objetos (POO). Aprendimos a pensar en "objetos", esas pequeñas cápsulas de superpoderes (datos y comportamientos) que son la base de casi todo el software moderno. Ahora, vamos a construir sobre esos cimientos para levantar un rascacielos.

    Piensa en lo que hemos hecho hasta ahora como aprender a fabricar ladrillos (objetos). Cada ladrillo es útil, pero su verdadero poder se desata cuando los combinamos para construir algo más grande. En este tema, aprenderemos las técnicas de los maestros constructores de software: cómo relacionar esos ladrillos, cómo crear "ladrillos base" reutilizables y cómo hacer que distintas piezas encajen de manera flexible.

    Hablaremos de Herencia, que es como tener un molde maestro para crear nuevos tipos de ladrillos con características ya definidas. Exploraremos la Composición, que es como construir una pared uniendo distintos ladrillos, cada uno con su función. Y nos sumergiremos en el Polimorfismo, la magia que permite tratar distintos tipos de ladrillos como si fueran el mismo, haciendo nuestro código increíblemente flexible. ¿Listos para pasar de artesanos a arquitectos de software? ¡Vamos a ello!

    Herencia: El ADN del Código

    La herencia es uno de los pilares de la POO. Es un mecanismo que nos permite crear nuevas clases a partir de otras ya existentes. La nueva clase, llamada "clase hija" o "subclase", hereda los atributos y métodos de la clase existente, llamada "clase padre" o "superclase".

    Definición: Herencia

    Es una relación "es un/a". Permite que una clase (subclase) adquiera las propiedades y comportamientos (métodos) de otra clase (superclase). Piensa en ello como la genética: heredas rasgos de tus padres, pero también tienes tus propias características únicas. Un Coche es un Vehiculo, pero tiene atributos adicionales como el número de puertas.

    La principal ventaja es la reutilización de código. No tenemos que reescribir el código común una y otra vez.

    En Java, utilizamos la palabra clave extends para indicar que una clase hereda de otra.

    Ejemplo 1: Jerarquía de Vehículos

    Imagina que estamos modelando distintos tipos de vehículos. Todos comparten características comunes: una marca, un modelo y la capacidad de moverse.

    // Clase Padre o Superclase
// La marcamos como "open" para permitir que otras clases hereden de ella.
// En Java, las clases son heredables por defecto, a menos que se marquen como "final".
public class Vehiculo {
    protected String marca;
    protected String modelo;

    public Vehiculo(String marca, String modelo) {
        this.marca = marca;
        this.modelo = modelo;
    }

    public void arrancar() {
        System.out.println("El vehículo ha arrancado.");
    }

    public String getInfo() {
        return "Marca: " + marca + ", Modelo: " + modelo;
    }
}

// Clase Hija o Subclase
public class Coche extends Vehiculo {
    private int numeroPuertas;

    public Coche(String marca, String modelo, int numeroPuertas) {
        // Llamada al constructor de la clase padre (Vehiculo)
        super(marca, modelo);
        this.numeroPuertas = numeroPuertas;
    }

    // Sobrescribimos el método arrancar para especializar el comportamiento
    @Override
    public void arrancar() {
        System.out.println("El coche " + marca + " " + modelo + " ha arrancado.");
    }

    // Añadimos un método propio de Coche
    public void tocarClaxon() {
        System.out.println("¡Beep, beep!");
    }

    @Override
    public String getInfo() {
        return super.getInfo() + ", Puertas: " + numeroPuertas;
    }
}

    La palabra super

    super es una palabra clave que nos da acceso a los miembros (métodos y atributos) de la clase padre. La usamos para: 1. Llamar al constructor del padre: super(marca, modelo); 2. Llamar a un método del padre desde un método sobrescrito: super.getInfo();

    Ejemplo 2: Figuras Geométricas

    Otro ejemplo clásico es el de las figuras geométricas. Todas tienen un área, pero se calcula de forma diferente. Aquí, una clase abstract (que veremos más adelante) sería ideal, pero por ahora, usemos una clase base concreta.

    public class Figura {
    protected String color;

    public Figura(String color) {
        this.color = color;
    }

    public double getArea() {
        // Una figura genérica no tiene un área definida.
        return 0.0;
    }
}

public class Circulo extends Figura {
    private double radio;

    public Circulo(String color, double radio) {
        super(color);
        this.radio = radio;
    }

    // Sobrescritura obligatoria para un cálculo correcto
    @Override
    public double getArea() {
        return Math.PI * radio * radio;
    }
}

public class Rectangulo extends Figura {
    private double base;
    private double altura;

    public Rectangulo(String color, double base, double altura) {
        super(color);
        this.base = base;
        this.altura = altura;
    }

    @Override
    public double getArea() {
        return base * altura;
    }
}

    Composición: Construyendo con Bloques

    Si la herencia es la relación "es un/a", la composición es la relación "tiene un/a". En lugar de que una clase sea otra, una clase contiene una o más instancias de otras clases para construir una funcionalidad más compleja.

    Definición: Composición

    Es un principio de diseño que modela una relación "tiene un/a". Una clase compleja se construye a partir de otras clases más simples, conteniéndolas como atributos. Piensa en un coche: un Coche tiene un Motor, tiene Ruedas, tiene una Carroceria. El coche no es un motor, sino que usa un motor para funcionar.

    La composición es, en general, más flexible y recomendada que la herencia ("Favorecer la composición sobre la herencia" es un famoso principio de diseño).

    Ejemplo 1: El Coche y su Motor

    Un coche no es un motor, pero necesita uno para funcionar. En lugar de heredar de una clase Motor, la clase Coche tendrá un objeto Motor como uno de sus atributos.

    // La clase Motor es una pieza independiente
public class Motor {
    private String tipo;
    private int caballos;

    public Motor(String tipo, int caballos) {
        this.tipo = tipo;
        this.caballos = caballos;
    }

    public void encender() {
        System.out.println("Motor " + tipo + " encendido.");
    }

    public void apagar() {
        System.out.println("Motor apagado.");
    }
}

// La clase Coche "compone" o "tiene un" Motor
public class Coche {
    private String marca;
    private String modelo;
    private Motor motor; // Relación "tiene un"

    public Coche(String marca, String modelo, Motor motor) {
        this.marca = marca;
        this.modelo = modelo;
        this.motor = motor; // Inyección de dependencia
    }

    public void arrancar() {
        System.out.println("Arrancando el " + marca + " " + modelo + "...");
        motor.encender(); // Delega la acción al objeto compuesto
    }
}

// Uso
Motor motorV8 = new Motor("V8", 450);
Coche mustang = new Coche("Ford", "Mustang", motorV8);
mustang.arrancar();

    Inyección de Dependencias

    Fíjate en el constructor de Coche. No crea el objeto Motor dentro de sí mismo (new Motor(...)), sino que lo recibe como un parámetro. Esto se llama Inyección de Dependencias y es una práctica fundamental. Hace que la clase Coche sea más flexible, ya que podemos "inyectarle" cualquier tipo de motor que cumpla el contrato, sin tener que modificar la clase Coche.

    Ejemplo 2: Un Pedido y sus Productos

    Un pedido en una tienda online no es un producto, sino que contiene una lista de productos.

    public class Producto {
    private String nombre;
    private double precio;

    public Producto(String nombre, double precio) {
        this.nombre = nombre;
        this.precio = precio;
    }

    public double getPrecio() {
        return precio;
    }
    // ... otros getters y setters
}

public class Pedido {
    private int id;
    private List<Producto> productos; // Relación "tiene varios"

    public Pedido(int id) {
        this.id = id;
        this.productos = new ArrayList<>();
    }

    public void agregarProducto(Producto producto) {
        productos.add(producto);
    }

    public double calcularTotal() {
        double total = 0.0;
        for (Producto p : productos) {
            total += p.getPrecio(); // Delega el cálculo parcial
        }
        return total;
    }
}

// Uso
Producto laptop = new Producto("Laptop Pro", 1200.00);
Producto raton = new Producto("Ratón Inalámbrico", 25.00);

Pedido miPedido = new Pedido(101);
miPedido.agregarProducto(laptop);
miPedido.agregarProducto(raton);

System.out.println("Total del pedido: " + miPedido.calcularTotal()); // Salida: Total del pedido: 1225.0

    Clases Abstractas: El Boceto del Artista

    A veces, queremos crear una clase base que sirva como una plantilla, pero que por sí misma no tenga sentido instanciar. Por ejemplo, ¿qué es un "Vehículo" genérico? No puedes comprar "un vehículo", compras un "coche", una "moto", etc.

    Definición: Clase Abstracta

    Es una clase que no puede ser instanciada directamente. Funciona como un "boceto" o plantilla para sus subclases. Puede contener tanto métodos concretos (con implementación) como métodos abstractos (sin implementación). Las clases hijas están obligadas a implementar todos los métodos abstractos de la clase padre.

    Se usan para: * Compartir código común entre clases relacionadas. * Definir un "contrato" que las clases hijas deben cumplir, forzándolas a implementar ciertos métodos.

    Se declaran con la palabra clave abstract.

    Ejemplo 1: Figuras Geométricas (versión mejorada)

    Nuestro ejemplo anterior de Figura es un candidato perfecto para ser una clase abstracta. No tiene sentido crear un objeto Figura, y queremos obligar a todas las subclases a que definan cómo se calcula su área.

    public abstract class Figura {
    protected String color;

    public Figura(String color) {
        this.color = color;
    }

    // Método abstracto: sin cuerpo, solo la firma.
    // Obliga a las subclases a implementarlo.
    public abstract double getArea();

    // Método concreto: compartido por todas las subclases.
    public String getColor() {
        return color;
    }
}

public class Circulo extends Figura {
    private double radio;

    public Circulo(String color, double radio) {
        super(color);
        this.radio = radio;
    }

    // Implementación obligatoria del método abstracto
    @Override
    public double getArea() {
        return Math.PI * radio * radio;
    }
}

// Si intentamos esto, el compilador dará un error:
// Figura miFigura = new Figura("Rojo"); // ERROR: 'Figura' is abstract; cannot be instantiated

    ¡No puedes instanciar lo abstracto!

    El error del compilador al intentar new Figura() es la esencia de las clases abstractas. Son un contrato, un plano, no el edificio terminado.

    Ejemplo 2: Empleados de una Empresa

    En una empresa, hay distintos tipos de empleados (programadores, diseñadores, gerentes), pero todos son "Empleados" y comparten la necesidad de calcular su salario, aunque la fórmula sea diferente para cada uno.

    public abstract class Empleado {
    protected String nombre;
    protected String id;

    public Empleado(String nombre, String id) {
        this.nombre = nombre;
        this.id = id;
    }

    // Método abstracto: cada tipo de empleado calculará su salario de forma distinta.
    public abstract double calcularSalario();

    // Método concreto: todos los empleados tienen un nombre.
    public String getNombre() {
        return nombre;
    }
}

public class Programador extends Empleado {
    private double salarioBase;
    private int horasExtra;

    public Programador(String nombre, String id, double salarioBase) {
        super(nombre, id);
        this.salarioBase = salarioBase;
        this.horasExtra = 0;
    }

    public void registrarHorasExtra(int horas) {
        this.horasExtra = horas;
    }

    @Override
    public double calcularSalario() {
        // Fórmula específica para programadores
        return salarioBase + (horasExtra * 40.0);
    }
}

    Interfaces: El Contrato de Funcionalidad

    Mientras que una clase abstracta define lo que un objeto es, una interfaz define lo que un objeto puede hacer. Es un contrato puro que especifica un conjunto de métodos que una clase debe implementar.

    Definición: Interfaz

    Una interfaz es una colección de métodos abstractos (y constantes). Una clase que implements una interfaz se compromete a proporcionar una implementación para todos los métodos de esa interfaz. Es un contrato de comportamiento.

    Una de las grandes ventajas de las interfaces es que una clase puede implementar múltiples interfaces, algo que no es posible con la herencia de clases (en Java no hay herencia múltiple de clases).

    Característica Clase Abstracta Interfaz
    Relación "es un/a" (Is-A) "puede hacer" (Can-Do)
    Herencia Múltiple No (una clase solo puede extends una clase) Sí (una clase puede implements varias interfaces)
    Constructores Sí puede tener No puede tener
    Atributos Puede tener cualquier tipo de atributo Solo constantes (public static final por defecto)
    Métodos Puede tener métodos abstractos y concretos Todos los métodos son public abstract por defecto (desde Java 8 pueden tener default y static methods)

    Ejemplo 1: Objetos "Voladores"

    No todos los objetos que vuelan son pájaros. Un avión también vuela. La herencia no nos sirve aquí, pero una interfaz Volador sí.

    public interface Volador {
    // Todos los métodos en una interfaz son public abstract por defecto
    void despegar();
    void volar();
    void aterrizar();
}

public class Pajaro implements Volador {
    @Override
    public void despegar() {
        System.out.println("El pájaro bate sus alas para despegar.");
    }

    @Override
    public void volar() {
        System.out.println("El pájaro planea en el cielo.");
    }

    @Override
    public void aterrizar() {
        System.out.println("El pájaro busca una rama para aterrizar.");
    }
}

public class Avion implements Volador {
    @Override
    public void despegar() {
        System.out.println("El avión acelera en la pista y despega.");
    }

    @Override
    public void volar() {
        System.out.println("El avión vuela a 10,000 metros de altura.");
    }

    @Override
    public void aterrizar() {
        System.out.println("El avión despliega el tren de aterrizaje y aterriza.");
    }
}

    Ejemplo 2: Comparable para Ordenar

    Java nos proporciona interfaces muy útiles. Una de ellas es Comparable, que permite a los objetos de una clase definir su propio "orden natural" y, por tanto, ser ordenados en colecciones.

    // Hacemos que la clase Alumno implemente la interfaz Comparable
public class Alumno implements Comparable<Alumno> {
    private String nombre;
    private int nota;

    public Alumno(String nombre, int nota) {
        this.nombre = nombre;
        this.nota = nota;
    }

    public String getNombre() { return nombre; }
    public int getNota() { return nota; }

    @Override
    public String toString() {
        return "Alumno [nombre=" + nombre + ", nota=" + nota + "]";
    }

    // Implementamos el único método de la interfaz: compareTo
    // Este método define el orden. Queremos ordenar por nota, de mayor a menor.
    @Override
    public int compareTo(Alumno otro) {
        // Si this.nota es mayor que otro.nota, debe ir antes (resultado negativo)
        // Si son iguales, resultado 0.
        // Si this.nota es menor, debe ir después (resultado positivo).
        return Integer.compare(otro.nota, this.nota); // Orden descendente
    }
}

// Uso:
List<Alumno> clase = new ArrayList<>();
clase.add(new Alumno("Ana", 8));
clase.add(new Alumno("Luis", 5));
clase.add(new Alumno("Juan", 10));

Collections.sort(clase); // ¡Magia! Collections.sort sabe cómo ordenar Alumnos

System.out.println(clase);
// Salida: [Alumno [nombre=Juan, nota=10], Alumno [nombre=Ana, nota=8], Alumno [nombre=Luis, nota=5]]

    Métodos default y static en Interfaces (desde Java 8)

    Desde Java 8, las interfaces pueden tener métodos con implementación. - default: Proporciona una implementación por defecto que las clases pueden usar o sobrescribir. - static: Son métodos de utilidad que pertenecen a la interfaz misma, no a las instancias.

    public interface Notificable {
    void enviarNotificacion(String mensaje);

    default void log(String mensaje) {
        System.out.println("LOG: " + mensaje);
    }
}

    Polimorfismo: Una Esencia, Múltiples Formas

    El polimorfismo es la habilidad de un objeto de presentarse de diferentes formas. Es el resultado de combinar herencia e interfaces. Nos permite escribir código que puede operar con objetos de una superclase o interfaz, sin necesidad de conocer el tipo específico del objeto en tiempo de compilación.

    Definición: Polimorfismo

    Del griego "muchas formas". Es la capacidad de procesar objetos de diferentes tipos y clases a través de una única interfaz uniforme. En la práctica, significa que puedes tener una referencia de tipo padre que apunta a un objeto de tipo hijo, y cuando llamas a un método, Java ejecutará la versión del método correspondiente al objeto hijo (la versión sobrescrita).

    El polimorfismo es lo que hace que nuestro código sea flexible, desacoplado y extensible.

    Ejemplo 1: La Orquesta Polimórfica

    Imagina una orquesta. El director le dice a un músico "toca", pero el sonido que se produce depende del instrumento. El violín sonará como un violín y la trompeta como una trompeta.

    // Clase base abstracta
public abstract class Instrumento {
    public abstract void tocar();
}

public class Violin extends Instrumento {
    @Override
    public void tocar() {
        System.out.println("Suena una melodía de violín...");
    }
}

public class Trompeta extends Instrumento {
    @Override
    public void tocar() {
        System.out.println("¡Suena una fanfarria de trompeta!");
    }
}

// El director de orquesta usa el polimorfismo
public class Orquesta {
    public void iniciarConcierto(List<Instrumento> instrumentos) {
        for (Instrumento i : instrumentos) {
            i.tocar(); // ¡Magia polimórfica aquí!
        }
    }
}

// Uso
List<Instrumento> misInstrumentos = new ArrayList<>();
misInstrumentos.add(new Violin());
misInstrumentos.add(new Trompeta());
misInstrumentos.add(new Violin());

Orquesta miOrquesta = new Orquesta();
miOrquesta.iniciarConcierto(misInstrumentos);
    La llamada i.tocar() es polimórfica. Java, en tiempo de ejecución, mira qué objeto real está almacenado en i y llama al método tocar() de esa clase específica (Violin o Trompeta).

    Ejemplo 2: Procesando Figuras

    Podemos usar el polimorfismo para manejar una colección de figuras diferentes de manera uniforme.

    // Reutilizamos las clases Figura, Circulo y Rectangulo

public class Lienzo {
    public void dibujarTodo(List<Figura> figuras) {
        for (Figura f : figuras) {
            System.out.println("Dibujando un " + f.getClass().getSimpleName() + 
                               " de color " + f.getColor() + 
                               " con área " + f.getArea());
        }
    }
}

// Uso
List<Figura> misFiguras = new ArrayList<>();
misFiguras.add(new Circulo("Rojo", 5.0));
misFiguras.add(new Rectangulo("Azul", 4.0, 6.0));
misFiguras.add(new Circulo("Verde", 2.5));

Lienzo miLienzo = new Lienzo();
miLienzo.dibujarTodo(misFiguras);

    Cuidado con el instanceof

    Aunque a veces es necesario, abusar del operador instanceof para comprobar el tipo de un objeto y hacer un casting puede ser una señal de un mal diseño. 

    // Intenta evitar esto si es posible
if (vehiculo instanceof Coche) {
    Coche c = (Coche) vehiculo;
    c.tocarClaxon();
}
    Un buen uso del polimorfismo a menudo elimina la necesidad de estas comprobaciones.

    La clase Object en Java: El Ancestro Universal

    En Java, existe una clase muy especial que es, directa o indirectamente, la superclase de todas las demás clases. Es la cima de la jerarquía de herencia.

    Definición: La Clase Object

    Es la clase raíz de la jerarquía de clases en Java. Cada clase es descendiente de Object. Esto significa que cada objeto que creas hereda los métodos de Object.

    Esto tiene una implicación muy potente: cualquier variable de tipo Object puede contener una referencia a cualquier tipo de objeto en Java.

    Métodos Fundamentales de Object

    Aunque Object tiene varios métodos, hay tres que son cruciales para entender y que a menudo necesitarás sobrescribir.

    Método Descripción ¿Por qué sobrescribirlo?
    toString() Devuelve una representación en String del objeto. Por defecto, es el nombre de la clase + @ + el hashcode del objeto (ej: Coche@15db9742). Para proporcionar una representación legible y útil del estado de tu objeto (ej: "Coche [marca=Ford, modelo=Mustang]").
    equals(Object obj) Compara si dos objetos son "iguales". Por defecto, compara si son el mismo objeto en memoria (identidad, ==). Para definir tu propia lógica de "igualdad de contenido" (ej: dos objetos Alumno son iguales si tienen el mismo DNI).
    hashCode() Devuelve un valor int (código hash) para el objeto. Contrato equals-hashCode: Si sobrescribes equals(), DEBES sobrescribir hashCode(). La regla es: si a.equals(b) es true, entonces a.hashCode() debe ser igual a b.hashCode(). Es esencial para el funcionamiento de colecciones como HashSet y HashMap.

    Ejemplo Práctico: Sobrescribiendo equals, hashCode y toString

    Vamos a crear una clase Punto y a implementar correctamente estos métodos.

    import java.util.Objects;

public class Punto {
    private int x;
    private int y;

    public Punto(int x, int y) {
        this.x = x;
        this.y = y;
    }

    // Sobrescritura de toString() para una representación clara
    @Override
    public String toString() {
        return "Punto [x=" + x + ", y=" + y + "]";
    }

    // Sobrescritura de hashCode()
    // Es crucial para que colecciones como HashSet funcionen correctamente.
    // Usamos Objects.hash para generar un buen hash a partir de los campos.
    @Override
    public int hashCode() {
        return Objects.hash(x, y);
    }

    // Sobrescritura de equals() para comparar por contenido
    @Override
    public boolean equals(Object obj) {
        // 1. Misma referencia: son idénticos.
        if (this == obj) return true;
        // 2. El otro es nulo o de una clase diferente: no pueden ser iguales.
        if (obj == null || getClass() != obj.getClass()) return false;
        // 3. Hacemos el casting y comparamos los campos relevantes.
        Punto punto = (Punto) obj;
        return x == punto.x && y == punto.y;
    }
}

// Uso
Punto p1 = new Punto(10, 20);
Punto p2 = new Punto(10, 20);
Punto p3 = new Punto(30, 40);

System.out.println("p1.toString(): " + p1); // Llama a nuestro toString()
System.out.println("p1 == p2: " + (p1 == p2)); // false, son objetos diferentes en memoria
System.out.println("p1.equals(p2): " + p1.equals(p2)); // true, gracias a nuestro `equals()`
System.out.println("p1.equals(p3): " + p1.equals(p3)); // false

    ¡El Contrato equals-hashCode es Sagrado!

    Romper el contrato entre equals() y hashCode() puede causar comportamientos muy extraños e inesperados, especialmente cuando usas HashSet o HashMap. Si dos objetos son iguales según equals(), DEBEN tener el mismo hashCode. La inversa no es obligatoria, pero un buen hashCode minimiza colisiones.

    Aplicación en el Mundo Real

    Estos conceptos no son solo teoría académica; son el pan de cada día en el desarrollo de software profesional.

    • Frameworks como Spring: Utilizan masivamente la Inyección de Dependencias y las Interfaces para lograr un bajo acoplamiento. Tú defines un "contrato" (una interfaz, como UsuarioRepository) y Spring se encarga de "inyectar" la implementación concreta (UsuarioRepositoryImpl) donde la necesites. Esto hace que el código sea increíblemente modular y fácil de testear.

    • Desarrollo de Videojuegos: La Herencia y el Polimorfismo son fundamentales. Puedes tener una clase base Enemigo con un método atacar(). Luego, creas subclases como Orco, Dragon y Esqueleto. Cada uno implementa atacar() de forma diferente. El motor del juego simplemente puede tener una lista de Enemigos y llamar a atacar() en cada uno, sin preocuparse del tipo específico.

    • APIs Gráficas (UI Toolkits): En JavaFX o Swing, casi todos los componentes visuales (botones, etiquetas, paneles) heredan de una clase base común (como Node o Component). Esto permite tratarlos de forma polimórfica: puedes tener una colección de Components y aplicarles operaciones comunes, como cambiar su visibilidad o color.
