    Acceso a BD Relacionales

    Imagina que tu aplicación Java es un camarero muy eficiente: recoge la comanda, la traduce al idioma de la cocina y trae el plato de vuelta. JDBC es precisamente ese traductor entre tu código y la base de datos relacional.^1

    Conceptos Fundamentales

    Definición: JDBC

    JDBC significa Java Database Connectivity. Es la API estándar de Java para conectarse a bases de datos relacionales, enviar SQL, leer resultados y gestionar conexiones.^3

    Definición: Driver

    Un driver JDBC es el componente concreto que entiende el protocolo de una base de datos específica, como MySQL o MariaDB. La API es común, pero el driver es el “intérprete” particular de cada SGBD.^2

    Definición: Connection

    Representa una sesión abierta con la base de datos. Desde ella se crean sentencias, se controlan transacciones y se liberan recursos al terminar.^1

    Definición: Statement

    Es el objeto que envía sentencias SQL a la base de datos. Sirve para ejecutar consultas simples, comandos DML y operaciones que devuelven resultados.^5

    Definición: ResultSet

    Es el conjunto de filas devuelto por una consulta SELECT. Funciona como una tabla temporal con un cursor que avanza fila a fila.^1

    Definición: PreparedStatement

    Es una variante de Statement preparada para consultas parametrizadas. Evita concatenar cadenas, mejora la seguridad y suele rendir mejor cuando la consulta se reutiliza.^1

    Definición: DAO

    DAO significa Data Access Object. Es un patrón que separa el acceso a datos del resto de la aplicación, como si la parte de “hablar con la BD” fuese un departamento especializado.^1

    Tip

    Piensa en JDBC como una autopista común y en el driver como el peaje que conoce la salida exacta para cada base de datos. Si cambias de motor, normalmente cambias el peaje, no todo el coche.

    Desarrollo y Ejemplos Prácticos

    1. Desfase objeto-relacional

    En Java trabajas con objetos; en una base de datos relacional guardas filas y columnas. Ese “desfase” obliga a transformar datos de un mundo a otro, igual que pasar de un archivo de Excel a un JSON bien formado sin perder información. En la práctica, eso explica por qué el código de acceso a datos necesita una capa específica y no debería quedar repartido por toda la aplicación.^1

    // Entidad simple en Java
public class Cliente {
    private Long id;
    private String nombre;
    private String ciudad;

    public Cliente(Long id, String nombre, String ciudad) {
        this.id = id;
        this.nombre = nombre;
        this.ciudad = ciudad;
    }

    public Long getId() { return id; }
    public String getNombre() { return nombre; }
    public String getCiudad() { return ciudad; }
}

    // Mapeo manual de una fila de BD a un objeto Java
Cliente cliente = new Cliente(
    rs.getLong("id"),
    rs.getString("nombre"),
    rs.getString("ciudad")
);
    En Java En BD relacional
    Objeto Fila
    Atributo Columna
    Colección de objetos Conjunto de registros
    Métodos No existen como tal en la tabla

    Idea clave

    El desfase no es un error; es una realidad del diseño. Lo importante es que tu código lo resuelva de forma ordenada y no con “cables pelados” por todas partes.

    Danger

    No metas SQL en la capa de presentación. Eso es como poner la cocina en mitad del salón: al principio parece práctico, pero luego nadie encuentra nada.

    // Mala práctica: SQL mezclado con interfaz o lógica dispersa
String sql = "SELECT * FROM clientes WHERE ciudad = '" + ciudad + "'";

    // Mejor: separar datos y comportamiento
String sql = "SELECT * FROM clientes WHERE ciudad = ?";
PreparedStatement ps = conn.prepareStatement(sql);
ps.setString(1, ciudad);

    3. ¿Qué problema tiene concatenar valores directamente en una consulta SQL?
    4. ¿Cómo explicarías el desfase objeto-relacional a alguien que solo conoce Excel?


    2. Protocolos de acceso: ODBC y JDBC

    ODBC fue una solución muy influyente para acceder a distintas bases de datos desde aplicaciones externas, pero está más ligado a entornos nativos y a una arquitectura menos natural para Java. JDBC, en cambio, nace para Java y encaja mejor con su filosofía multiplataforma y orientada a interfaces.^1^2

    // JDBC: conexión estándar en Java
String url = "jdbc:mysql://localhost:3306/tienda";
Connection conn = DriverManager.getConnection(url, "root", "clave");

    // Ejemplo de lectura simple
Statement st = conn.createStatement();
ResultSet rs = st.executeQuery("SELECT nombre FROM clientes");
while (rs.next()) {
    System.out.println(rs.getString("nombre"));
}
    Aspecto ODBC JDBC
    Lenguaje principal C / APIs nativas Java
    Portabilidad Menor Alta
    Integración en Java Forzada Natural
    Uso actual en FP Más conceptual Muy práctico

    Tip

    Si ODBC es un traductor con acento muy local, JDBC es un traductor que ya nació hablando el idioma de Java. El resultado: menos fricción y menos drama en clase.

    Warning

    No confundas “acceso a datos” con “almacenamiento de datos”. Una cosa es cómo llegas a la BD y otra cómo organiza internamente sus tablas el SGBD.

    // Estructura típica en Java
package acceso;

public class ConexionBD {
    private ConexionBD() {}
}

    // Esquema típico de uso

    3. Arquitectura JDBC y funcionamiento

    La arquitectura JDBC se apoya en varias piezas: DriverManager, Connection, Statement y ResultSet. DriverManager localiza el driver adecuado, Connection abre la sesión, Statement ejecuta la sentencia y ResultSet devuelve el resultado. En versiones actuales de Java, java.sql sigue siendo el paquete base de la API JDBC.^1^3

    Detalle práctico

    En Java moderno, algunos drivers se auto-registran, pero en clase sigue siendo útil entender Class.forName(...) porque aclara qué driver estás cargando y por qué.

    Danger

    Cerrar Statement y Connection no es opcional. Dejar conexiones abiertas es como dejar pestañas del navegador abiertas durante semanas: al final todo va lento y nadie sabe por qué.

    4. Consultas de descripción de datos

    Las consultas de descripción de datos sirven para conocer la estructura de la BD: tablas, vistas, columnas y metadatos. En JDBC, esto se hace con DatabaseMetaData, que permite inspeccionar el catálogo como si fuese un mapa del sistema. Es muy útil cuando no conoces del todo la BD o cuando necesitas generar herramientas automáticas.^1

    Connection conn = DriverManager.getConnection(url, user, pass);
DatabaseMetaData meta = conn.getMetaData();

System.out.println(meta.getDatabaseProductName());
System.out.println(meta.getDriverName());
System.out.println(meta.getURL());

    ResultSet tablas = meta.getTables(null, "tienda", null, new String[]{"TABLE"});
while (tablas.next()) {
    System.out.println(tablas.getString("TABLE_NAME"));
}

    ResultSet columnas = meta.getColumns(null, "tienda", "clientes", null);
while (columnas.next()) {
    System.out.println(columnas.getString("COLUMN_NAME") + " - " + columnas.getString("TYPE_NAME"));
}

    Tip

    DatabaseMetaData es perfecto para crear herramientas de inspección o administración. Es como abrir la caja fuerte con un plano, no a ciegas.

    Warning

    No confundas metadatos con los datos reales de negocio. Saber que existe una tabla clientes no significa haber leído todavía un solo cliente.

    // Obtener solo tablas
String[] tipos = {"TABLE"};
ResultSet rsTablas = meta.getTables(null, null, "%", tipos);

    // Obtener columnas de una tabla concreta
ResultSet rsCols = meta.getColumns(null, null, "clientes", null);

    5. Consultas DML y consultas parametrizadas

    Las consultas DML son las que modifican datos: INSERT, UPDATE y DELETE. Para consultas dinámicas, PreparedStatement es la opción más segura y limpia porque separa la estructura SQL de los valores. En la práctica, es el equivalente a preparar una plantilla y rellenar huecos, en vez de escribir el documento desde cero cada vez.^1

    String sql = "INSERT INTO clientes(nombre, ciudad) VALUES(?, ?)";
PreparedStatement ps = conn.prepareStatement(sql);
ps.setString(1, "Ana");
ps.setString(2, "León");
int filas = ps.executeUpdate();

    String sql = "UPDATE clientes SET ciudad = ? WHERE id = ?";
PreparedStatement ps = conn.prepareStatement(sql);
ps.setString(1, "Madrid");
ps.setLong(2, 10L);
ps.executeUpdate();

    String sql = "DELETE FROM clientes WHERE id = ?";
PreparedStatement ps = conn.prepareStatement(sql);
ps.setLong(1, 10L);
ps.executeUpdate();
    Opción Ventaja Riesgo
    Statement Simple para SQL fijo Más exposición a errores y concatenaciones
    PreparedStatement Parámetros y reutilización Requiere preparar la consulta
    executeQuery Lee datos No sirve para INSERT/UPDATE/DELETE
    executeUpdate Modifica datos No devuelve ResultSet

    Danger

    Evita concatenar datos del usuario en SQL. Eso abre la puerta a inyección SQL, el equivalente técnico a dejar la caja registradora sin llave.

    // Malo
String sql = "SELECT * FROM clientes WHERE nombre = '" + nombre + "'";

    // Bueno
String sql = "SELECT * FROM clientes WHERE nombre = ?";
PreparedStatement ps = conn.prepareStatement(sql);
ps.setString(1, nombre);

    Buena práctica

    PreparedStatement no solo mejora la seguridad. También ayuda a que el código sea más legible, más mantenible y menos propenso a errores de comillas.

    // Borrado controlado
String sql = "DELETE FROM clientes WHERE ciudad = ?";
PreparedStatement ps = conn.prepareStatement(sql);
ps.setString(1, "Oviedo");
int eliminados = ps.executeUpdate();

    3. ¿Qué ventaja tiene reutilizar la misma consulta con distintos valores?

    6. Singleton y DAO

    Cuando una aplicación crece, no conviene abrir conexiones “a lo loco” por cada esquina del código. El patrón Singleton permite tener una única instancia de conexión compartida, mientras que DAO concentra el acceso a datos en clases especializadas. En conjunto forman una combinación muy típica en aplicaciones Java del lado servidor.^1

    public class ConexionBD {
    private static Connection conn = null;
    private static final String URL = "jdbc:mysql://localhost:3306/tienda";
    private static final String USER = "root";
    private static final String PASS = "clave";

    private ConexionBD() {
    }

    public static Connection getConnection() throws SQLException {
        if (conn == null || conn.isClosed()) {
            conn = DriverManager.getConnection(URL, USER, PASS);
        }
        return conn;
    }
}

    public class ClienteDAO {
    public List<Cliente> findAll() throws SQLException {
        List<Cliente> lista = new ArrayList<>();
        String sql = "SELECT id, nombre, ciudad FROM clientes";

        try (Connection conn = ConexionBD.getConnection();
             Statement st = conn.createStatement();
             ResultSet rs = st.executeQuery(sql)) {

            while (rs.next()) {
                lista.add(new Cliente(
                    rs.getLong("id"),
                    rs.getString("nombre"),
                    rs.getString("ciudad")
                ));
            }
        }
        return lista;
    }
}

    Tip

    DAO es como el departamento de logística de una empresa. La dirección no habla directamente con cada almacén; manda una solicitud al área que sabe cómo hacerlo bien.

    Warning

    No mezcles en la misma clase interfaz gráfica, reglas de negocio y SQL. Eso termina siendo un “código lasaña”: muchas capas, poca digestión.

    // Ejemplo de uso desde la aplicación
ClienteDAO dao = new ClienteDAO();
List<Cliente> clientes = dao.findAll();

    // Ejemplo de método de borrado en DAO
public int deleteById(long id) throws SQLException {
    String sql = "DELETE FROM clientes WHERE id = ?";
    try (Connection conn = ConexionBD.getConnection();
         PreparedStatement ps = conn.prepareStatement(sql)) {
        ps.setLong(1, id);
        return ps.executeUpdate();
    }
}

    Aplicación en el Mundo Real

    JDBC sigue siendo una base muy presente en sistemas empresariales, especialmente en aplicaciones Java que trabajan con MySQL, MariaDB, PostgreSQL u Oracle. Aunque hoy muchos proyectos usan frameworks como Spring Data o Hibernate, debajo suele seguir habiendo JDBC, como el motor oculto de un coche eléctrico: no lo ves, pero empuja.^1^4

    En empresas pequeñas y medianas, JDBC es ideal para herramientas internas, paneles administrativos, microservicios sencillos y ejercicios formativos con control total del SQL. También es muy útil cuando quieres un acceso fino a la base de datos sin depender de una capa ORM compleja. Para el alumnado de DAW, dominarlo es clave porque ayuda a entender qué pasa “bajo el capó” antes de subir al nivel framework.^1

    En proyectos reales, el patrón DAO aparece en sistemas de inventario, ERPs, CRM, plataformas de reservas y backends de e-commerce. Separar conexión, consulta y modelo de datos hace que el proyecto escale mejor y se pruebe con más facilidad. Además, facilita cambiar de motor de base de datos o migrar parte del acceso a otro repositorio sin reescribir toda la aplicación.^1
